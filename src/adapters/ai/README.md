# Frontière IA V1

Le moteur décide ; les adapters extraient et formulent. Les modifications P10 présentes dans la branche restent nécessaires à la validation des ellipses.

- `extractMessage` demande une extraction brute avec onze exemples fixes, dont un délai textuel relatif sans date inventée, puis `convertRawExtraction` contrôle le contrat complet et les citations avant de réutiliser les validations du moteur. Seul `validation.valid` peut être transmis au merge existant. `missing` n'est pas une observation. `ambiguous` et `provided` sans normalisation restent observables dans `unresolved`, sans choix de cible ni clarification inventée.
- A propose désormais `intent`: `provide`, `correct`, `remove` ou `unknown`. `provided` transporte provide/correct avec valeur ; remove utilise provided + intent remove + value null. unknown utilise le statut et l’intention unknown ; missing/ambiguous utilisent intent null. Les anciens JSON sans intent gardent uniquement le mapping historique provide/unknown ; aucune correction n’est inférée. P3 valide les intentions sensibles, puis le merge existant décide. Une contradiction seule ne devient jamais correct.
- `askedQuestionsAtStart` est aussi transmis à A, avec field et question canonique, sans état du dossier ni pending globaux. Il aide à comprendre sans imposer une affectation par ordre. Le même contexte reste transmis à la validation P10 ; il ne donne aucune autorisation nouvelle aux ellipses ambiguës.
- `formulateQuestions` reçoit des questions canoniques déjà décidées par le code. Le code contrôle cardinalité, ordre, identifiants et format ; il n'ajoute aucun contenu métier. La fidélité sémantique des reformulations relève des consignes du modèle et n'est pas prouvée par ces contrôles structurels.
- `answerFromFacts` est uniquement la primitive C. Aucun provider n'est appelé si les facts sont absents. Le code appelant doit avoir décidé de leur suffisance. Le prompt impose les sources uniques, les nuances, les réponses partielles et l'absence de choix arbitraire devant une contradiction. Un JSON conforme ne prouve pas l'appui factuel de chaque phrase.

## RAG non câblé et raccordement prospect

Les champs text/enum peuvent déclarer `semanticNormalizations`, une liste locale d'équivalences `{ sourceText, normalizedValue }`. Une citation entière correspondant à l'entrée autorise cette cible non littérale (texte ou clé enum). Le rapprochement de la citation utilise la normalisation existante de casse, espaces et apostrophes ; la cible doit être exactement celle configurée. Sans équivalence, le support littéral reste requis. A reçoit ces données ; la conversion les vérifie avant les validations du moteur. Une équivalence ne contourne ni les citations exactes du message, ni les options enum, ni P3/P10. Ce mécanisme ne prétend pas prouver toute paraphrase libre et n'ajoute aucun dictionnaire global.

Le dépôt ne contient ni facts documentaires réels, ni catégories configurées, ni mapping fiable question → catégorie, ni critère de suffisance. Le RAG V1 et le déclenchement automatique de C sont donc arrêtés à cette frontière, conformément à la spécification. Aucun classement, fact, résolution de contradiction ou schéma de stockage métier n'est inventé.

La qualification, la sélection de questions et la gestion des conflits restent dans le code. Le flux prospect est désormais raccordé par `adapters/prequalification/processMessage.ts` et `/api/prequalification`, avec l'état explicitement retransmis par l'UI. Aucun stockage ni session serveur n'est ajouté. Voir [la documentation du flux](../prequalification/README.md). La route prototype reste disponible et réutilise le client Groq partagé et son modèle inchangé.

Les tests injectent un provider mocké et ne prouvent pas le comportement sémantique d'un modèle réel. Aucun test local ne dépend du réseau ou de la clé Groq. La clé est lue uniquement dans le module Node `adapters/groq.ts` ; ce module ne doit pas être importé dans une interface navigateur.
